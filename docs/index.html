NIH Harvester

A complete, nationwide pull of NIH RePORTER project records — FY1985 to present — with a schema-on-read design and an adaptive pagination strategy that gets full coverage despite NIH's 10,000-record cap.

Overview

This project pulls a full project record for every NIH RePORTER application, nationwide, with no institution scoping, into a local SQLite database. Rather than flattening each API response into typed columns at load time, it stores each record's raw JSON verbatim and layers two derived views on top for querying so nothing NIH returns is ever dropped, truncated, or silently lost.

It was validated on a single institution's own NIH-funded portfolio, then generalized into a nationwide pull and a worked tutorial: the real difficulty isn't the data model, it's getting every record back from an API that hard-caps pagination at 10,000 results per query.

Why schema-on-read

The common approach flatten each response into one typed column per field as you load it is fragile. If you also restrict which fields you request, two decisions (which fields to ask for, and which columns to store) end up made twice, in two different places, and either one can silently drop data if it's wrong. If NIH adds a field later, or a value grows past whatever width you picked, it just vanishes with no error.

This pipeline avoids both failure modes. include_fields is never set, and each record's raw JSON is stored verbatim in one column, with only appl_id, project_num, core_project_num, and fiscal_year promoted out for indexing. The nih_parsed view flattens it back out for convenient querying a read-time convenience on top of an unmodified archive, not a decision made once at load time.

The hard problem: pagination at scale

NIH RePORTER's /v2/projects/search endpoint caps offset + limit at 10,000, so you can never page past the first 10,000 matches of a query no matter how many more exist. That's a non-issue for a single institution. Nationwide, fiscal-year totals run 50,000–94,000, and even the single largest NIH institute (NCI) in a peak year is 12,590 on its own, over the cap by itself.

Dual-pass

Paginate the same query once ascending by appl_id, once descending. The two 10,000-record windows necessarily overlap once the true total is under 20,000, so their union is guaranteed to cover every record verified against a real 12,590-record bucket (NCI, FY2010): exactly 12,590/12,590.

Split by agency, only above 20,000

An earlier version split by NIH's ~27 current institutes/centers as a fixed list measurably not enough, covering only 70% of FY1985 (missing defunct codes like NCRR and non-NIH agencies like AHRQ, FDA). No fixed list is reliable across 40 years of agency reorganizations, so agency codes are discovered from a real sample of that year's data and cross-checked against a broad fallback list closing the gap from 70% to 99.4%+. Two gap-fill passes close the rest: stage 1b re-splits by activity code, and stage 1c compares each year's records on file with NIH's own total per activity code and per agency, and fetches every bucket that comes up short. Every fiscal year now holds every record NIH reports for it.

A confirmed API gotcha, four times over

Every criteria field tested silently accepts its documented camelCase spelling (matching NIH's own swagger spec) but does nothing no error, just the unfiltered result set. The working spelling is snake_case, undocumented anywhere:

Field camelCase (spec) snake_case (works)
Organization type organizationType organization_type
Date added dateAdded / fromDate date_added / from_date
Activity codes activityCodes activity_codes
Org states orgStates org_states

Pipeline

  1. 1_harvest_raw.py

    Nationwide pull, every fiscal year, one JSONL file per year. An interruption only costs the in-progress year a .done marker means a rerun skips completed years.

  2. 2_load_to_sqlite.py

    Loads every fy*.jsonl into nih_harvester.db. Idempotent: hashes existing rows first, only inserts new / updates changed / skips unchanged.

  3. Derived views

    nih_parsed flattens the raw JSON into ~50 columns; nih_indicators layers a worked multi-year-funding classification on top.

Schema

nih_raw_projects — the landing table:

appl_id            INTEGER PRIMARY KEY   -- NIH's unique id per fiscal-year application record
project_num        TEXT
core_project_num   TEXT
fiscal_year        INTEGER
raw_json           TEXT NOT NULL         -- the full API record, verbatim
row_hash           TEXT NOT NULL         -- sha256 of raw_json's canonical form
valid_from         TEXT
valid_to           TEXT                  -- unused for now; reserved for future use
is_current         INTEGER NOT NULL DEFAULT 1
Worth knowing about the MYF classification: it's narrow and requires the budget period to exactly match the project period, which most fiscal-year records don't, since NIH typically funds one year at a time via non-competing continuations.
